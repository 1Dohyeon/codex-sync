# 리뷰 공통 절차

[`diff-review`](../diff-review/SKILL.md)·[`branch-review`](../branch-review/SKILL.md)·[`pr-review`](../pr-review/SKILL.md)가 공유하는 뒷부분이다.
각 스킬이 범위와 축을 확정한 뒤 이 문서를 읽고 그대로 이어서 진행한다.

한 모델이 여러 영역을 한 컨텍스트에서 순차로 보면 앞 영역이 뒤 영역 판단에 섞인다.
그래서 영역별로 격리된 리뷰어를 병렬로 돌리고, 취합만 상위 모델이 한다.

## 요구사항 확보

코드를 지적하기 전에 무엇을 만들려던 것인지 먼저 안다. 요구사항 없이 diff만 보면 의도된 동작을 버그로 올리게 된다.

사용자에게 먼저 묻지 않고 아래 순서로 찾는다.

1. **사용자가 이번 요청에 요구사항을 붙여넣었으면 그것이 원문이다.** 다른 출처를 찾지 않고 그대로 쓴다.
2. 붙여넣은 것이 없으면 스킬마다 아래를 본다.

| 스킬                          | 출처                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------- |
| `diff-review`·`branch-review` | 현재 브랜치의 계획 문서 `requirements.md` → 없으면 PR 설명·커밋 메시지·이번 대화 |
| `pr-review`                   | PR 헤드 브랜치의 계획 문서 → 없으면 PR 설명과 거기서 이어지는 이슈·링크          |

3. 그래도 없으면 아래 "못 찾았을 때"로 간다.

### 계획 문서

계획 문서의 위치와 역할은 [`planning-dev`](../planning-dev/SKILL.md)에 있다.

- [`planning-dev`의 "계획 문서 찾기"](../planning-dev/SKILL.md#계획-문서-찾기) 순서로 찾고, 찾은 폴더의 `requirements.md`를 Read한다.
- 그 순서의 4번(완료 위치)에서 하는 확인 질문은 위의 "사용자에게 먼저 묻지 않고"의 예외다. 찾은 문서가 이번 작업의 것인지는 사용자만 알 수 있다.
- 요구사항은 `requirements.md`의 번호 붙은 요구사항이고, 요구사항마다 적힌 확인 기준이 그대로 판정 기준이 된다. 배경은 맥락으로만 넘긴다.
- `design.md`·`tasks.md`는 구현 계획이므로 요구사항으로 넘기지 않는다.

**`pr-review`에서는 `{branch}`가 다르다.** 남의 브랜치이므로 현재 체크아웃된 브랜치가 아니라 PR의 헤드 브랜치로 찾는다. checkout 확인 때 이미 얻은 `headRefName`을 `{branch}`로 넘긴다.

- 그 순서로 찾아도 문서가 없으면 스스로 뒤지지 말고 사용자에게 위치를 묻는다. 사용자가 "없다"고 하면 PR 설명으로 내려간다.
- 이 문서는 **사용자가 작성한 것이지 PR 작성자가 받은 요구가 아닐 수 있다.** 그래서 아래 "출처를 밝힌다"가 특히 중요하다.

### PR 설명을 쓸 때 (`pr-review` 전용)

```sh
gh pr view <번호> --json title,body
```

설명에 이슈나 문서 참조가 있으면 **거기까지 따라가서 원문을 얻는다.** 한 줄짜리 설명이어도 참조 하나로 기획 원문에 닿는 경우가 많다.

- `#12`, `Closes #12` 같은 참조가 있으면 `gh issue view 12`로 읽는다.
- Notion 링크가 있으면 `notion-fetch`로 읽는다. 다른 링크는 `WebFetch`로 읽는다.
- 도구가 없거나 인증·권한 오류로 열리지 않으면 Claude in Chrome으로 사용자의 브라우저에서 그 링크를 열어 본다. 쓰기 전에 `claude-in-chrome` 스킬을 읽는다. 이것까지 안 되면 그 사실을 밝히고 넘어간다. **열지 못한 링크의 내용을 제목이나 URL로 미루어 지어내지 않는다.**

본문은 세 종류가 섞여 있으므로 갈라서 넘긴다. 판별 기준은 하나다. **diff를 보지 않고도 쓸 수 있었던 문장인가.**

| 종류      | 예                                     | 처리                                  |
| --------- | -------------------------------------- | ------------------------------------- |
| 요구      | "결합 할인이 목록에 노출되어야 한다"   | 요구사항으로 넘긴다                   |
| 배경      | "고객사에서 안 보인다는 문의가 왔다"   | 맥락으로만 넘긴다. 판정 대상이 아니다 |
| 구현 서술 | "`getCombineList`에서 필터를 제거했다" | **넘기지 않는다**                     |

- **구현 서술을 요구사항으로 쓰지 않는다.** diff를 말로 옮긴 것이라, 그것으로 대조하면 코드로 만든 잣대로 코드를 재는 셈이 되어 무엇이든 통과한다.
- 요구가 하나도 없고 배경만 있으면 배경을 뒤집어 약한 요구로 쓸 수 있다("안 보인다" → "보여야 한다"). 코드가 아니라 사람이 쓴 문장에서 끌어내는 것이라 자기참조가 아니다. 다만 출처가 약하므로 그 사실을 함께 넘긴다.
- 분류 결과(요구 몇 개, 배경 몇 개, 제외한 구현 서술 몇 개)를 리포트 머리에 적는다. 요구사항 축의 결과를 얼마나 믿을지 판단하는 근거가 된다.

### 못 찾았을 때

- 위 순서로 찾아도 없으면 그때 사용자에게 요구사항 원문(이슈·기획서)을 요청한다.
- 사용자가 "없다" 또는 "그냥 봐 달라"고 하면 그대로 진행한다. 리뷰 자체를 막지는 않는다.
- 그 경우 각 에이전트에게 요구사항이 없다는 사실을 명시해서 넘기고, 리포트 머리에도 적는다. 의도와 다르다는 종류의 지적은 근거가 없으므로 세우지 않게 한다.

### 출처를 밝힌다

어느 출처에서 얻었는지를 에이전트에 함께 넘기고 리포트 머리에도 적는다. 같은 지적이라도 출처가 무엇이냐에 따라 무게가 다르기 때문이다.

```
요구사항 출처: 사용자가 붙여넣은 텍스트
요구사항 출처: 계획 문서 `feature/combine-modal/requirements.md` (사용자 작성)
요구사항 출처: PR 설명 + 연결 이슈 #12
요구사항 출처: PR 설명의 배경 문장에서 끌어냄 (약함)
요구사항 없음
```

출처가 약하다고 표시된 것에서 나온 지적은 등급을 올리지 않는다. 판정 근거가 흔들리므로 `참고`나 "확인 필요"에 둔다.

### 계획을 그대로 믿지 않는다

계획 문서는 사용자가 승인한 계획이지만 계획 자체가 틀렸을 수 있다. 아래 검증 단계는 "요구사항에 명시된 동작"을 지적에서 버리게 되어 있으므로, 계획대로 동작하는데도 결과가 틀려 보이면 버리지 말고 "확인 필요"로 옮긴다.

## 대상 고정

에이전트에 명령을 넘기면 각자 실행하므로, 그사이 워킹트리가 바뀌면 축마다 다른 코드를 보게 된다. 커밋 전 변경을 리뷰할 때 특히 그렇고, 그러면 중복 병합과 상반 판정이 모두 어긋난다. 그래서 상위가 한 번만 떠서 파일로 고정한다.

각 스킬이 확정한 명령의 출력을 스크래치패드에 저장한다. 스크래치패드 경로는 세션마다 다르므로 시스템 프롬프트에 적힌 것을 쓴다.

```sh
<스킬이 확정한 명령> > <스크래치패드>/review.diff
```

이 파일이 이번 리뷰의 유일한 대상이며, 이후 워킹트리가 바뀌어도 리뷰 범위는 흔들리지 않는다.

`diff-review`는 "지금 커밋하면 올라갈 것 전부"가 범위다. `git diff HEAD`는 추적되지 않은 파일을 담지 않으므로, 스냅샷 명령 앞에 저장소 루트에서 `git add -N .`(새 파일 intent-to-add, `.gitignore` 대상 제외), 뒤에 `git reset`(인덱스만 되돌림)을 붙인다. `-N`은 내용을 스테이징하지 않아 실제 커밋에 영향이 없다. `branch-review`·`pr-review`는 커밋된 범위라 이 처리가 필요 없다.

## 규모 판단

이번 리뷰의 규모와 유형을 먼저 정하고, 그에 따라 부를 축을 정한다. 규모와 유형의 정의는 [`planning-dev/sub/analyze-task.md`](../planning-dev/sub/analyze-task.md)의 "유형과 규모"에 있다.

### 규모 정하기

1. 요구사항 확보에서 `requirements.md`를 읽었으면 머리에 적힌 유형과 규모를 1차 값으로 쓴다.
2. 스냅샷을 잰다. 아래 실측표는 `analyze-task.md`의 세 기준 가운데 "수정 파일"을 diff로 잰 근사치다. "새 의존성·계약"과 "설계상 선택지"는 diff만으로 잴 수 없어 1차 값으로 반영되므로, 3에서 둘 가운데 큰 쪽을 쓴다.

```sh
wc -l <스크래치패드>/review.diff
```

| 실측           | 판정 기준                              | 조치                                                            |
| -------------- | -------------------------------------- | --------------------------------------------------------------- |
| 비어 있음      | 0줄                                    | 중단하고 그 사실만 보고한다                                     |
| 너무 큼        | 2000줄 초과 **또는** 파일 50개 초과    | 그대로 넘기지 않는다. 규모를 알리고 범위를 좁혀 달라고 요청한다 |
| 실행 코드 없음 | 실행되는 코드 파일이 하나도 없음       | 서브에이전트를 부르지 않고 상위가 컨벤션 축만 직접 훑는다       |
| trivial        | 실행되는 코드 파일 1개, 변경 20줄 이하 | 아래 "부를 축"                                                  |
| small          | 실행되는 코드 파일 1개                 | 아래 "부를 축"                                                  |
| standard       | 실행되는 코드 파일 2~5개               | 아래 "부를 축"                                                  |
| large          | 실행되는 코드 파일 6개 이상            | 아래 "부를 축"                                                  |

3. 1차 값과 실측 가운데 **큰 쪽**을 쓴다. 실측이 더 작다고 규모를 내리지 않는다. 안 띄워서 놓치는 쪽이 띄워서 낭비하는 쪽보다 나쁘다.

- 파일 수는 스킬이 정한 방법으로 센다(`git diff --stat`의 요약 줄, 또는 `gh pr diff <번호> --name-only`).
- "실행되는 코드 파일"은 소스·스크립트·빌드 설정처럼 동작에 영향을 주는 파일이다. 문서·문구·주석만 바뀐 것은 여기 들지 않는다.
- 정의에서 최소 standard로 올리는 경로(인증, 입력 처리, DB 등)를 diff가 건드리면 실측도 최소 standard로 본다.
- 계획 문서가 없으면 실측만 쓴다. 유형을 알 수 없으면 아래 유형별 축은 붙이지 않는다.
- 애매하면 한 단계 위로 본다.
- 정한 규모·유형과 그 근거(문서 값인지 실측인지)를 리포트 머리에 적는다.
- 실행 코드 없음 구간과 trivial 구간이라도 아래 **검증 규칙은 그대로 적용한다.** 상위가 직접 만든 지적도 `file:심볼`을 열어 근거 인용을 확인하고, 판정 사실을 못 대면 세우지 않는다.
- 너무 큼 구간에서 사용자가 그대로 진행하라고 하면 진행하되, 깊이가 얕아진다는 점을 리포트에 적는다.

### 부를 축

| 규모     | `branch-review`·`pr-review`                                           | `diff-review`     |
| -------- | --------------------------------------------------------------------- | ----------------- |
| trivial  | 서브에이전트를 부르지 않고 상위가 코드 레벨·컨벤션 관점으로 직접 본다 | 같음              |
| small    | `logic-reviewer`·`impact-reviewer`·`convention-reviewer`              | 스킬이 정한 세 축 |
| standard | 여섯 축 모두                                                          | 스킬이 정한 세 축 |
| large    | 여섯 축 모두. 범위를 나눌 수 있으면 나눠 달라고 한 번 권한다          | 스킬이 정한 세 축 |

`branch-review`·`pr-review`에서 small이면 유형에 따라 축을 더 붙인다. standard 이상은 이미 여섯 축이라 더할 것이 없다.

| 유형              | 더 붙이는 축            | 이유                             |
| ----------------- | ----------------------- | -------------------------------- |
| 버그 수정         | `testing-reviewer`      | 회귀 테스트가 있는지 본다        |
| 새 기능·동작 변경 | `requirement-reviewer`  | 요구대로 만들었는지 본다         |
| 리팩터링          | `architecture-reviewer` | 구조를 바꾼 작업이라 구조를 본다 |

- `diff-review`는 유형별 축을 붙이지 않는다. 그 세 축이 미완성 상태에서 오탐을 내는 이유가 [`diff-review`](../diff-review/SKILL.md)의 "축"에 있다.
- 스킬이 정한 제외 조건이 이 표보다 우선한다. `pr-review`에서 체크아웃하지 않으면 `impact-reviewer`를 빼고, 요구사항이 없으면 `requirement-reviewer`를 뺀다.
- `qa-reviewer` 부록은 규모와 관계없이 화면에 닿는 파일이 있으면 부른다.

## 병렬 호출

**한 응답에서** 위 "부를 축"에서 정한 서브에이전트를 동시에 호출한다. 순차로 부르지 않는다.

모델은 각 에이전트 정의의 `model`이 정한다. 호출할 때 따로 지정하지 않는다. 호출부를 열지 않고 함수 안에서 판정하는 [`logic-reviewer`](../../agents/logic-reviewer.md)와 정답이 정해져 있지 않은 설계 판단을 내리는 [`architecture-reviewer`](../../agents/architecture-reviewer.md)는 Opus이고 나머지는 Sonnet인데, 다른 축은 문서·설정·인접 코드·Grep 결과와 대조하면 끝나는 일이라 최상위 모델이 필요하지 않기 때문이다.

**결과를 기다리는 동안 중간 보고를 하지 않는다.** 축이 하나씩 도착할 때마다 "몇 개 도착했다"고 한 턴씩 쓰면 그만큼 끝이 밀린다. 전부 모일 때까지 기다렸다가 아래 검증으로 바로 넘어간다.

각 호출 프롬프트에 다음을 그대로 넘긴다.

- **스냅샷 파일의 절대경로를** 넘긴다. 각 에이전트는 그 파일을 Read해서 대상을 잡으며, 범위를 다시 추론하게 두지 않는다. 명령을 넘기지 않는다.
- 저장소 파일은 디스크에서 그대로 열어 주변 구조와 대조하라고 함께 적는다. 스냅샷은 무엇이 바뀌었는지를 담을 뿐, 주변 코드는 담지 못한다.
- 추적되지 않은 파일을 포함하기로 했으면 그 경로 목록도 함께 넘긴다.
- 확보한 요구사항 원문을 그대로 싣는다. 못 얻었으면 "요구사항 원문 없음, 의도와 다르다는 종류의 지적은 세우지 말 것"이라고 명시한다.
- "자기 영역만 보고 다른 영역은 지적으로 세우지 말 것" - 각 에이전트 정의에 이미 있으나 한 번 더 못박는다.

### 조건이 붙는 축

- **요구사항 원문을 못 얻었으면 [`requirement-reviewer`](../../agents/requirement-reviewer.md)를 부르지 않는다.** 대조할 것이 없으면 추측만 하게 된다. 부르지 않았다는 사실을 리포트 머리에 적는다.
- **디스크가 리뷰 대상 브랜치가 아니면 [`impact-reviewer`](../../agents/impact-reviewer.md)를 부르지 않는다.** 이 축은 저장소를 Grep해서 참조 지점을 찾는 것이 일의 전부라, 디스크가 다른 상태면 찾아낸 참조가 전부 헛것이 된다. [`pr-review`](../pr-review/SKILL.md)에서 체크아웃하지 않기로 한 경우가 여기 해당한다. 부르지 않았다는 사실을 리포트 머리에 적는다.
- **스냅샷에 화면에 닿는 파일(컴포넌트·스타일·라우트)이 하나도 없으면 [`qa-reviewer`](../../agents/qa-reviewer.md)를 부르지 않는다.** 프론트가 아닌 저장소에서 매번 빈 목록이 붙는 것을 막는다.
- `qa-reviewer`는 지적을 내지 않는 부록이다. 다른 축과 함께 병렬로 띄우되 결과는 아래 검증을 거치지 않는다.

## 검증

결과가 다 온 뒤, 취합보다 **먼저** 한다. 격리된 에이전트는 컨텍스트가 부족한 상태로 판단하므로 오탐이 반드시 섞인다.

이 단계는 추론이 아니라 대조다. 각 지적에는 근거 인용과 축별 판정 사실이 붙어 오므로, 그것이 실제 코드와 맞는지만 확인하면 된다. 지적마다 파일을 처음부터 읽어 에이전트의 판단을 역추적하지 않는다.

지적 하나하나를 아래로 거른다.

- **인용문을 대조한다.** 지목된 `file:심볼`을 Read해서 근거 인용이 그 안에 그대로 있는지 본다. 없으면 버린다. 행 번호가 어긋난 것만으로는 버리지 않는다. 기준은 심볼이다.
  - **`impact-reviewer`의 인용은 깨지는 쪽에서 대조한다.** 이 축은 바뀐 코드가 아니라 그 변경을 받아내지 못하는 코드를 인용하므로, 열어야 할 파일은 diff에 없을 수 있다. 지적이 지목한 영향 지점의 `file:심볼`을 열어 본다.
- **판정 사실이 비었으면 옮긴다.** 축이 내야 할 사실(실행 조건과 결과, 영향 지점, 확장 비용, 현재 테스트, 강제 여부)이 없으면 지적에서 빼고 "확인 필요"로 옮긴다. 그 사실이 없으면 등급을 매길 수 없다.
- **`impact-reviewer`의 `[impact-확인]` 항목은 검증하지 않는다.** 그 축이 스스로 단정하지 못한다고 밝힌 것이므로 지적이 아니다. 아래 출력의 "확인 필요"로 그대로 옮긴다.
- **의심스러운 사실만 표적으로 확인한다.** 실행 조건이 미심쩍은 항목만 그 호출부를 연다. 모든 지적의 주변을 다 훑지 않는다.
- **요구사항에 명시된 동작은 버린다.** 확보한 요구사항이 그렇게 동작하라고 적고 있으면 지적이 아니다. 다만 위 "계획을 그대로 믿지 않는다"에 걸리면 버리지 말고 "확인 필요"로 옮긴다.
- **누락 지적은 대조 방식이 다르다.** `requirement-reviewer`가 낸 누락 항목은 지목할 심볼이 없어 코드 인용을 대조할 수 없다. 대신 요구사항 인용이 원문에 그대로 있는지 확인하고, 그 항목이 적은 "찾아본 곳"을 Grep해서 정말 없는지 본다. 이미 구현돼 있으면 버린다.

살리려고 지적을 고쳐 쓰지 않는다. 확인되지 않으면 버리는 것이 맞다.

받은 지적 수와 통과한 수를 세어 리포트에 적는다. 무엇이 왜 걸러졌는지까지 나열할 필요는 없다.

## 취합

검증을 통과한 것만 대상으로 한다. 이 단계에서 **새로운 지적을 만들지 않는다.**

- 같은 지적이 둘 이상 에이전트에서 나오면 하나로 합치고, 어느 영역들에서 나왔는지 적는다.
- 에이전트 간 결론이 상반되면 **해소하지 말고 양쪽을 나란히 드러낸다.** 판단은 사용자 몫이다.
- 코드 레벨 축과 영향 범위 축은 경계가 맞닿아 있어 같은 심볼을 양쪽이 집을 수 있다. 이때는 **지적이 가리키는 위치로 가른다.** 바뀐 함수 안을 가리키면 코드 레벨 축의 것이고, 그 함수를 쓰는 다른 곳을 가리키면 영향 범위 축의 것이다. 둘이 같은 원인의 앞뒤면 하나로 합치되 영향 지점을 함께 싣는다.

### 등급을 매긴다

에이전트는 등급을 붙이지 않는다. 축마다 "높음"의 뜻이 달라 그대로 쓸 수 없기 때문이다. 대신 각 축이 판정에 필요한 사실을 내놓으므로, 상위는 그 사실을 **하나의 기준으로** 환산한다.

| 등급      | 판정 근거                                                                                                                                                                           |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `막음`    | 실행되는 경로에서 결과가 틀리거나 데이터가 손상된다 / 기존 호출부가 실제로 깨진다(빌드·타입·런타임) / 린터·CI가 실패시킨다 / 문서가 명시적으로 금지한 것을 어겼다                   |
| `고칠 것` | 드문 입력에서만 깨진다 / 깨지는 곳이 테스트 코드뿐이다 / 강제되지는 않으나 지배적 패턴을 벗어난다 / 같은 요구가 또 오면 여러 곳을 고쳐야 한다 / 바뀐 핵심 동작에 대응 테스트가 없다 |
| `참고`    | 결과는 맞고 개선 여지만 있다 / 참조 지점은 바뀌었으나 동작은 그대로다 / 중복·정리 수준이다                                                                                          |

축이 무엇이든 이 세 등급으로 통일한다. 컨벤션 위반이 `막음`일 수도 있고 아키텍처 지적이 `참고`일 수도 있다.

판정 근거에 해당하는 사실이 지적에 없으면 등급을 추측하지 않는다. "확인 필요"로 옮긴다.

## 출력

마크다운 리포트 하나로 낸다. `ReportFindings` 도구는 쓰지 않는다.

- **맨 앞에 "먼저 고칠 것" 요약을 둔다.** 축을 가로질러 `막음`과 `고칠 것`만 모아 등급 순으로 나열한다. 이 부분만 읽어도 무엇부터 손댈지 알 수 있어야 한다.
- 그 아래에 이번에 부른 축별로 상세를 두고, 각 축 안에서는 등급 순으로 나열한다.
- 각 항목은 등급, 위치(`file:심볼`), 근거 인용, 문제, 제안. 축이 낸 판정 사실도 그대로 싣는다. 행 번호는 참고값이므로 적더라도 심볼 뒤에 괄호로 둔다.
- 축에 지적이 없으면 "지적 없음"으로 표기하고 그 축이 무엇을 확인했는지 한 줄 남긴다.
- 리포트 머리에 단서를 적는다: 이번에 부른 축, 검증에서 걸러진 건수, 요구사항 원문이 없었다는 사실, 규모가 상한을 넘어 깊이가 얕아졌다는 사실.
- 마지막에 "확인 필요"와 에이전트 간 상반된 결론을 따로 모아 적는다.

### 부록

지적과 섞지 않고 리포트 맨 뒤에 둔다.

- **브라우저에서 확인할 것**: `qa-reviewer`의 목록을 그대로 싣는다. 등급을 붙이지 않는다. 다만 각 항목의 `근거`에 적힌 `file:심볼`이 실재하는지 확인해서, 없는 화면을 지어낸 항목은 뺀다. 뺀 건수는 적는다.
