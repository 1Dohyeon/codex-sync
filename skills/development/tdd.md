# 테스트를 먼저 쓴다

구현할 때는 [`SKILL.md`](./SKILL.md)의 "테스트로 검증"에서, 계획을 세울 때는 [`planning-dev`](../planning-dev/SKILL.md)의 `design.md`·`tasks.md`를 쓸 때 이 문서를 읽는다.

## 적용 범위

- 저장소 규칙이 테스트 범위·명령·파일 위치를 정해 두었으면 그것을 따른다. 저장소 규칙을 찾는 범위는 [`SKILL.md`](./SKILL.md)의 "규칙 우선순위"와 같다.
- 정해 둔 것이 없으면 프로세스 경계를 넘지 않는 로직(순수 함수, 계산·변환·판정 로직)에 적용한다.
- 화면, 창, 외부 프로세스, 파일 시스템, 네트워크, DB처럼 경계를 넘는 부분은 흉내 낸 테스트로 덮지 않고 실제로 실행해 확인한다. 흉내로 덮으면 흉내가 맞는지를 다시 확인해야 한다.
- 테스트 러너가 없는 저장소에는 새로 들이지 않는다. 그 사실을 사용자에게 알리고, 실행해서 확인한다.

## 절차

1. 기대하는 동작을 테스트로 먼저 쓴다. 위치와 이름은 저장소 관례를 따르고, 관례가 없으면 대상 파일 옆에 둔다.
2. 그 테스트만 돌려 실패를 확인한다(RED).
   - 써 두기만 하고 실행하지 않은 테스트는 RED가 아니다.
   - 실패 원인은 기대한 동작이 없다는 것이어야 한다. import 오류, 오타, 설정 문제로 난 실패는 RED가 아니다. 대상이 아직 없으면 함수 틀만 두고 돌린다.
   - RED를 확인하기 전에는 프로덕션 코드를 고치지 않는다.
3. 통과시킬 만큼만 구현하고, 같은 명령으로 통과를 확인한다(GREEN).
4. 정리할 것이 있으면 리팩터링하고, 전체 테스트가 통과하는지 확인한다.
5. RED와 GREEN을 확인한 실행 결과를 보고에 남긴다. 계획 문서가 있으면 `tasks.md`에도 남긴다.

## 유형별 첫 테스트

- 기존 기능을 고칠 때(동작 변경·버그 수정·리팩터링)는 고치기 전에 지금 동작을 코드나 실행으로 먼저 확인하고, 바뀌는 심볼의 호출부를 먼저 파악한다.
- 새 기능: 새 동작을 표현하는 실패 테스트를 먼저 쓴다.
- 동작 변경: 기존 테스트를 새 요구에 맞게 먼저 고치고, 그 테스트가 통과하도록 구현을 바꾼다.
- 버그 수정: 버그를 재현하는 테스트를 먼저 쓰고, 원인을 좁힌 뒤 고친다. 원인을 특정하지 못했으면 증상만 가리는 수정을 하지 않고, 확인한 것과 모르는 것을 나눠 보고한다.
- 리팩터링: 전후로 테스트가 통과하는지로 검증한다. 새 테스트는 필요할 때만 쓴다.
- 유효성 검사 추가: 유형과 관계없이 실패 케이스 테스트를 먼저 쓴다.

## 테스트가 아니라 구현을 고친다

테스트가 실패하면 구현을 고친다. 테스트 쪽이 틀렸다고 판단되면, 고치기 전에 왜 틀렸는지 먼저 말한다.

## 계획에 반영

- `design.md`의 테스트 전략에는 요구사항 번호마다 테스트로 확인할지, 실행해서 확인할지를 적는다.
- `tasks.md`에서 테스트 태스크는 그 테스트를 통과시키는 구현 태스크보다 앞에 둔다. 적용 범위 밖이라 실행해서 확인할 항목은 확인 태스크로 따로 적는다.
